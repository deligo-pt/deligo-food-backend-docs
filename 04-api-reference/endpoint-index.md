# API Endpoint Index

## Overview

Full inventory of HTTP endpoints exposed by the Deligo backend, generated by reading every `*.route.ts` file under `src/app/modules/*` and cross-referencing `src/app/routes/index.ts` (the central mounter) and `openapi.json`. Not derived from `openapi.json` alone — the route files are the primary source, since `openapi.json` is a hand/tool-maintained static file with no confirmed automated generation from code.

## Purpose

Let a developer find, for any feature, which endpoint to call, which roles/permissions it requires, and which controller/service implements it — without reading every route file directly.

## Base URL & Conventions

- All application routes are mounted under **`/api/v1`** (`src/app.ts`, `src/app/routes/index.ts`).
- Auth: `Authorization: Bearer <accessToken>` header, or the `accessToken` httpOnly cookie set at login — either works.
- Response envelope (success): `{ "success": true, "message": "...", "meta"?: {...}, "data": {...} }` — see [`error-codes.md`](error-codes.md) for the error envelope.
- `auth(...roles)` — role-gated. `auth(...roles, [permissions])` — the trailing array is a permission-catalog check, applied only when the caller's role is `ADMIN` (checked live against the DB; see [`../02-authentication/permissions-and-rbac.md`](../02-authentication/permissions-and-rbac.md)). Routes with no `auth()` call are public.
- `openapi.json` (726KB, committed static file, 259 documented paths per direct inspection) and Swagger UI are served at `/openapi.json` and `/api-docs`, both gated by HTTP Basic Auth (`API_DOCS_USER`/`API_DOCS_PASSWORD`) plus a Redis-backed 10-device cap (`src/app/middlewares/apiDocsAuth.ts`).

## Edge Cases

- **Likely route-shadowing bug in `Order` routes**: `GET /orders/delivery-partner/dispatch-order` and `GET /orders/delivery-partner/current-order` are registered *after* `GET /orders/:orderId` in `order.route.ts`. Express matches routes in registration order, so a request to `/orders/delivery-partner/current-order` would match `/orders/:orderId` first (with `orderId = "delivery-partner"`) rather than reaching the intended handler — unless Express's specific ordering or an intermediate guard prevents this in practice. This is worth verifying directly against current routing behavior before relying on either endpoint; flagged here as observed from route declaration order, not confirmed via a live request. See also [`../08-known-gaps/technical-debt-and-todos.md`](../08-known-gaps/technical-debt-and-todos.md).
- `Invoice`'s single route uses a bespoke `invoiceDownloadAccess` middleware rather than the standard `auth(...)` guard — its exact access rule is not detailed here; consult `src/app/modules/Invoice/invoiceDownloadAuth.ts` directly if working on this endpoint.
- `DELETE /offers/permanent-delete/:offerId` accepts a `VENDOR` token at the route level, but the service layer rejects non-admin callers in practice (per `docs/offers-integration-guide.md`) — the route's role list is broader than the actual enforced permission.
