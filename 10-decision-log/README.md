# Decision Log

## Purpose

This log records significant architectural and business-rule decisions for the Deligo backend — not just *what* was built, but *why* one approach was chosen over the alternatives. It exists so a future engineer questioning "why is this built this way?" can find the reasoning instead of re-deriving or re-litigating it.

## Source of truth and honesty rule

**Do not fabricate historical decisions.** A decision record should only be created when the context, problem, and reasoning can be confirmed — either directly from the person who made the call, from a PR/commit description that explains the reasoning, or from direct project knowledge at the time of the decision. If the *reasoning* behind an existing piece of architecture cannot be confirmed (only the resulting code can be observed), do not write a decision record asserting a rationale — instead note the observation in `08-known-gaps/technical-debt-and-todos.md` or the relevant module doc as "design as observed, rationale not confirmed."

This document contains **no retroactively-reconstructed decision records** — rationale for pre-existing architecture (e.g. why `AuthUser`/profile is two-tier, why a branch is modeled as a `Vendor` with `role: SUB_VENDOR` rather than a dedicated `Branch` model) was out of scope for the initial documentation pass, since the actual motivations were not available to confirm. Some of these are documented as *observed architecture* in `03-modules/vendor-and-branches.md` and `01-overview/architecture-overview.md` without claiming a decision rationale. Entries below start from the point logging actually began (2026-08-20).

## Entries

### 2026-08-29 — ProductCategory is vendor-owned (not a global admin taxonomy); Product keeps exactly one `category`; `additionalCategories` dropped

Status: Accepted (supersedes the 2026-08-24 `additionalCategories[]` decision below)
Context: `ProductCategory` was a platform-wide, admin-curated list keyed to a `BusinessCategory`; vendors could only read the slice matching their business type. The product direction changed: a vendor's categories are that vendor's own customer-facing product groups, managed by the vendor, with admins only inspecting them.
Problem: Three coupled questions. (1) Where does ownership live — keep the admin taxonomy and add a vendor layer, or make `ProductCategory` itself vendor-owned? (2) Keep `businessCategoryId` on the category (business type explicit) or drop it (implied by the owning vendor)? (3) What happens to `Product.additionalCategories[]`, which existed to let one product surface under several of the shared categories?
Decision:
1. **Ownership**: `ProductCategory` gains a required `vendorId` (`ref 'Vendor'`) set server-side from the caller; all create/update/activate/deactivate/delete routes move to `VENDOR`/`SUB_VENDOR` and are scoped `{_id, vendorId: caller}`. A `SUB_VENDOR` branch is its own owner (same convention as `Product`/`AddonGroup`). Admins get read-only list/get across all vendors (optional `?vendorId=` filter). `BusinessCategory` is untouched (still admin-managed).
2. **Drop `businessCategoryId`** from `ProductCategory` entirely — a category's business type is now implied by its owning vendor's `businessDetails.businessType`. The old Product↔category "same business type" check becomes a pure "same vendor" ownership check (`validateCategoryOwnership` → `403 CATEGORY_NOT_OWNED_BY_VENDOR`). Uniqueness moves from global (`slug`, `name.en`) to per-vendor compound (`{vendorId,name.en}`, `{vendorId,slug}`). The `icon` and `description` fields were also dropped — a vendor's ProductCategory is now just a localized `name` + `slug` + `isActive` (its create/update routes become plain-JSON, no multipart upload); BusinessCategory and Cuisine keep their own images.
3. **Remove `additionalCategories` completely.** A product has exactly one `category`, owned by the product's vendor. Every discovery consumer (`?category=` filter, BOGO `buyCategoryId`, "browse vendors by category", Meilisearch `categoryIds`) drops its `$or` and matches the single field; `categoryIds` stays a length-1 array so the Meili contract is unchanged.
4. **Customer-facing listing is vendor-scoped**: `GET /product-categories` (customer) and `/product-categories/open` require `?vendorId=` (`400 VENDOR_ID_REQUIRED`) and return only that vendor's active categories — vendor categories are never presented as a global catalog.
5. **No data migration** — existing shared `ProductCategory` documents have no owner; on `test-development` they are treated as disposable and reseeded per-vendor by hand.
Reason: Vendor-owned is the actual product model — these categories are a vendor's storefront sections, not a platform taxonomy — so making `ProductCategory` itself the owned resource (rather than layering vendor scoping over an admin taxonomy) removes the whole "which business type does this belong to" indirection and the cross-vendor-name-collision problem in one move. With ownership explicit, `businessCategoryId` and `additionalCategories` were both scaffolding for the shared-taxonomy world: a single owned `category` per product is unambiguous for SKU generation, discovery, BOGO and copy-to-branch, and avoids the Analytics double-counting that the 2026-08-24 design had to carve out around.
Alternatives: Keep the admin taxonomy and add a parallel vendor-owned category type (rejected — two category concepts for one storefront need). Keep `businessCategoryId` auto-derived server-side (rejected — redundant once the owner is known, and still leaks the shared-taxonomy mental model). Keep `additionalCategories` as a vendor-scoped multi-tag (rejected — the requirement is explicitly one primary category per product; multi-tagging can be revisited later as its own feature if a real need appears).
Consequences: Breaking for any client that sent `businessCategoryId` on category create/update, relied on admin category writes, treated productCategory listing as global, or sent `additionalCategories` on a product. `copy-to-branch` must now clone the source category into the target branch (branches can't share the parent's category id). Deleting a `ProductCategory` still doesn't cascade to `Product.category`; instead soft- and permanent-delete are now blocked (`409 PRODUCT_CATEGORY_HAS_PRODUCTS`) while any non-deleted product references the category. Existing Meili docs carry stale multi-value `categoryIds` until `npm run meili:migrate` is run.
Affected Modules: Category, ProductCategory, Product, Offer, Vendor, Meilisearch, ActivityLog
Source References: `src/app/modules/ProductCategory/productCategory.{interface,model,validation,route,service,controller,messages,constant,utils}.ts` (standalone module split out of `Category/` on 2026-08-29, mounted at `/api/v1/product-categories`); `src/app/modules/Category/category.{interface,model,validation,route}.ts` (ProductCategory removed); `src/app/modules/Product/product.{interface,model,validation,messages}.ts`, `product.service.ts`, `createProduct.utils.ts` (`validateCategoryOwnership`), `updateProduct.utils.ts`, `product.utils.ts`; `src/app/utils/getPopulateOptions.ts`; `src/app/modules/Offer/offer.utils.ts`; `src/app/modules/Vendor/vendor.service.ts`; `src/app/modules/Meilisearch/meilisearch.utils.ts`, `meilisearch.interface.ts`; `src/app/modules/ActivityLog/activityLog.constant.ts`; commit n/a (uncommitted at time of writing)

### 2026-08-26 — Vendor Agreement: 1:N with Vendor, created lazily inside registration (not eagerly at account creation), auto-derived from the Vendor profile (not a separate form), and a global default DeliGo signatory (not the approving Admin)

Status: Accepted
Context: The original Agreement design was 1:1 with Vendor, identified by a manually-entered `agreementCode`, with its own OTP-based email verification separate from the Vendor account's own OTP verification. The business requirement changed: a Vendor must be able to sign multiple agreements over its lifetime (initial registration, later a POS device agreement, addenda, renewals, ...), the Agreement step must sit *inside* the existing Vendor Registration flow rather than beside it, and the Vendor should never have to re-enter data already captured during registration.
Problem: Four separate but related questions needed resolving together: (1) what's the right cardinality between Vendor and Agreement, (2) at what point in the registration timeline should the Agreement record actually be created, (3) where does the Agreement's legal/company data come from, and (4) who signs on DeliGo's behalf, and when is that identity determined.
Decision:
1. **Cardinality**: `Agreement.vendorId → Vendor._id`, 1:N. `agreementCode` and the unique `Agreement.email` constraint were removed entirely — an Agreement is looked up by `vendorId`/`agreementType`/`_id`, never a client-supplied code.
2. **Creation timing**: the Agreement is created lazily, only when the Agreement step is opened (`POST /agreements/vendor/:vendorId`) — inserted into the existing registration/onboarding flow immediately before the final submission (after details/documents update), never bundled into `POST /auth/register` or `POST /auth/register/onboard`. An earlier iteration of this same work briefly created the Agreement eagerly, inside `onboardUser`'s own transaction — this was corrected specifically because the Vendor already exists by the time registration reaches its later steps, and coupling Agreement creation to account creation forced Agreement's legal/company fields onto the account-creation payload for a step the Vendor hadn't reached yet.
3. **Data source**: the Agreement step is not a form. Its entire legal/company snapshot (`establishmentName`, `nif`, `contactNumber`, `email`, `headOfficeAddress`, `zipCode`, `country`, `companyIban`, `companyRepresentativeName`) is derived server-side from the Vendor's own already-submitted profile (`businessDetails`, `contactNumber`, `email`, `businessLocation`, `bankDetails`, `name`) at creation time, then copied — never a live reference. An earlier iteration made this step an independent manual form (the Vendor/Commercial re-typing the same company details a second time); this was reversed once it was pointed out the data was already captured during the existing Details-update step. The only two inputs actually collected at the Agreement step are the POS payment option and the signature.
4. **DeliGo-side signatory**: exactly one global default DeliGo authorized signatory, configured once in the existing `GlobalSettings` singleton (`agreement.{deligoSignatureUrl, deligoSignatoryName, deligoSignatoryRole}`), applied at finalization — explicitly never derived from whichever Admin performs the approving/finalizing action.
Reason: (1) Multiple agreements per vendor is a direct business requirement — a Vendor's relationship with DeliGo produces more than one legal artifact over its lifetime. (2) Creating the Agreement only when its own step is reached keeps Vendor account creation decoupled from Agreement-specific concerns, and matches the actual UX: the Vendor already exists (and has completed profile/document steps) well before an Agreement makes sense to reference. (3) Deriving the snapshot from the Vendor's profile removes duplicate data entry and the drift risk of two independently-typed copies of the same establishment name/NIF/contact info; a one-time copy (not a live reference) still protects the signed contract from silently changing if the Vendor edits their profile afterward. (4) A named, admin-configured default signatory is a real authorization control — signing authority should not implicitly follow from "whichever admin happened to click Approve," which was never a considered design, just an ambiguity worth foreclosing explicitly given how easily it could be assumed otherwise.
Alternatives: Keep Agreement 1:1 with Vendor (rejected — doesn't support the multi-agreement requirement). Create the Agreement eagerly at registration start, either self-contained or requiring its fields on the registration payload (rejected — couples two independently-timed concerns and was the actual earlier implementation, corrected). Make the Agreement step an explicit form independent of the Vendor profile (rejected — forces duplicate entry of data the Vendor already provided; corrected after initially being built this way as a "clean model" simplification). Derive the DeliGo signatory from the approving Admin's own profile (rejected — signing authority is a deliberate business/legal designation, not an implicit consequence of admin role assignment).
Consequences: A Vendor cannot open the Agreement step before completing Details-update (`400 VENDOR_PROFILE_INCOMPLETE_FOR_AGREEMENT`) — this is a hard dependency between two steps that were previously independent. Editing the default DeliGo signatory in `GlobalSettings` only affects agreements finalized *after* the change; already-`SIGNED` agreements keep whatever signature was applied at their own finalization time (not stored as a version history, just baked into that agreement's own `agentSignaturePath`). `AGREEMENT_TYPE` has only one registered value today, so the "future agreement types reuse this same mechanism" design is implemented but not yet exercised by any real second type.
Affected Modules: Agreement, Auth, Vendor, GlobalSetting
Source References: `src/app/modules/Agreement/agreement.service.ts` (`buildInitialAgreementSnapshotFromVendor`, `applyDeligoSignatureAndFinalize`, `assertVendorSelfAccess`), `agreement.model.ts`, `agreement.interface.ts`, `agreement.validation.ts`, `agreement.route.ts`; `src/app/modules/Auth/auth.service.ts` (`onboardUser`, `submitForApproval`, approval hook); `src/app/modules/GlobalSetting/globalSetting.model.ts`, `.interface.ts`, `.service.ts` (`getDeligoDefaultSignature`); commit n/a (uncommitted at time of writing)

### 2026-08-24 — Multi-category tagging added as an additive `additionalCategories[]` field, not a replacement of `category`

Status: Superseded by the 2026-08-29 vendor-owned-ProductCategory decision above — `additionalCategories` was removed entirely and `ProductCategory` became vendor-owned. The rest of this entry is kept for historical context.
Context: `Product.category` was a single required `ProductCategory` ref, so a product could only ever be discovered/filtered under one category. The ask was to let a vendor associate a product with more than one category for better browse/search discoverability.
Problem: Several existing subsystems (SKU generation, `copy-to-branch`'s business-type check, Analytics category-performance stats) are built around a product having exactly one, always-present category. Simply turning `category` into an array would have forced every one of those consumers to handle "which one is the real/primary one" ambiguity, and would have made `category` optional-feeling even though it needs to remain mandatory.
Decision: Keep `category` exactly as it was (required, scalar, still the source of truth for SKU generation and the `copy-to-branch` business-type check) and add a new, independent, optional field `additionalCategories: ProductCategory[]` (max 5, same business-type validation rule as `category`, deduped against it). Every discovery-oriented consumer (`?category=` product filter, BOGO `buyCategoryId` matching, vendor "browse by category" filter/badges, Meilisearch's new `categoryIds` filter) was extended to match primary **OR** additional via `$or`. Reporting-oriented consumers (Analytics category-performance) were deliberately left reading primary `category` only.
Reason: This is the smallest change that satisfies "tag a product into multiple categories" without touching the meaning of "the" category anywhere that already depended on there being exactly one. It also avoids a double-counting problem in Analytics: if a sale were credited to every one of a product's categories, category percentages would no longer sum to 100% of orders, making "popular category" figures misleading. Capping at 5 additional categories keeps tagging curated rather than becoming an unbounded free-for-all that dilutes search relevance.
Alternatives: Replace `category` with a single `categories: ProductCategory[]` array (first element = primary) — rejected, since it would require every existing single-category consumer to defensively unwrap an array and risks an empty-array edge case for a field that must never be unset. Attribute Analytics sales to every tagged category — rejected for the double-counting reason above; noted as a possible explicit future toggle if a stakeholder wants "reach" instead of "primary sales" reporting.
Consequences: A product's "true" popularity across all its tags is not visible in Analytics — only its primary category gets credit there, so a product tagged into 5 categories but reported as strong in only 1 may undercount its actual cross-category traction. `copy-to-branch` now has two different failure behaviors for the same conceptual check (primary category mismatch blocks the whole copy; additional-category mismatch silently drops just that tag) — intentional, but worth knowing if extending that endpoint further.
Affected Modules: Product, Offer, Vendor, Meilisearch, Analytics (explicitly excluded)
Source References: `src/app/modules/Product/product.model.ts`, `product.interface.ts`, `product.validation.ts`, `product.service.ts`, `createProduct.utils.ts` (`validateAdditionalCategories`), `updateProduct.utils.ts`; `src/app/modules/Offer/offer.utils.ts`; `src/app/modules/Vendor/vendor.service.ts`; `src/app/modules/Meilisearch/meilisearch.utils.ts`, `meilisearch.constant.ts`, `meilisearch.service.ts`, `meilisearch.controller.ts`; commit n/a (uncommitted at time of writing)

### 2026-08-20 — Delivery handoff verified via a customer-supplied OTP, not a proof photo

Status: Accepted
Context: The `Order` module's delivery-partner `DELIVERED` transition required a `deliveryProofImage` string — any photo the rider chose to upload, with no server-side check tying it to the actual customer or a successful handoff.
Problem: A photo the rider uploads is not evidence the order reached the right person — it only proves *a* photo was taken. The module already had a working precedent for this exact problem on the self-pickup side (`pickup.code`, a counter-verified code), but delivery orders had no equivalent handoff verification.
Decision: Replace `deliveryProofImage` entirely with `deliveryOtp` — a 6-digit code generated and pushed to the customer when the rider transitions the order to `PICKED_UP`, which the rider must then collect from the customer and submit to complete the `DELIVERED` transition. Verification happens inline inside the same `updateOrderStatusByDeliveryPartner` call (no separate verify endpoint), gating the status write and downstream payout/wallet side effects on a correct match, with a 5-attempt lockout per order.
Reason: Mirrors the already-proven `pickup.code` pattern in the same module (embedded on the `Order` document, plain-text since it's low-stakes and single-use, `select:false` by default) rather than introducing a second OTP mechanism — the Auth module's Redis-backed login OTP was available but would have added a second storage system for something that's 1:1 with an order's lifecycle and already fits the embedded-subdocument model. Folding verification into the existing `DELIVERED` status-update call (the same shape `deliveryProofImage` used) avoids a second round trip and keeps the rider-app contract close to what it replaced.
Alternatives: Keep `deliveryProofImage` alongside the OTP as a belt-and-suspenders check — rejected, the requirement was to use OTP only. A dedicated `POST /:orderId/verify-delivery-otp` endpoint separate from the status update — rejected in favor of the single atomic call, consistent with how `verifyPickupCode` and the vendor-side status update are separate only because pickup verification is done by the *vendor*, not the same actor performing the status transition.
Consequences: Delivery completion no longer has any photographic evidence — reintroducing that (e.g. for dispute resolution) would need a separate field/flow. Rider apps must add an OTP-entry step before `DELIVERED`; any client still sending only `deliveryProofImage` breaks against the new validation schema. The self-pickup code's "no lockout" gap is not repeated here — delivery OTP has a 5-attempt lockout, but there is correspondingly no reset endpoint yet if a rider does lock out.
Affected Modules: Order
Source References: `src/app/modules/Order/order.service.ts` (`updateOrderStatusByDeliveryPartner`), `order.model.ts`, `order.interface.ts`, `order.validation.ts`, `order.constant.ts` (`DELIVERY_OTP_LENGTH`, `DELIVERY_OTP_MAX_ATTEMPTS`); commit `deligo-food-delivery-server@8bcd1930`

## Guidance for contributors

- Write the record close to when the decision is made — motivations are hardest to reconstruct honestly after the fact.
- A decision record is not a design proposal — capture what was actually decided and (ideally) implemented, referencing the code that resulted.
- If a later decision reverses or replaces an earlier one, don't delete the old record — mark its `Status` as `Superseded by <new decision>` and link forward, so the history of reasoning stays intact.
- Prefer a small number of high-signal records (things a new engineer would genuinely wonder about) over logging every minor choice.
